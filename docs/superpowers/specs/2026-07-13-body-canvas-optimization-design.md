# Body 画布可靠性与结构优化设计

## 背景

Body 创作画布目前同时存在权限来源冲突、保存可靠性问题和前端热路径性能问题：

- 团队发布版本已经是能力、角色和流程的正式配置来源，但运行时仍叠加 `body_canvas_power`、`body_canvas_agent`、`body_canvas_team` 三套旧白名单。
- 自动保存失败后仍把失败快照标记为已保存，导致脏数据不再重试。
- 节点拖动、画布移动和缩放会在每一帧提交完整画布，并反复序列化所有节点。
- 节点缓存以新建对象的引用相等作为命中条件，实际上不会命中。
- 能力目录和能力表单缓存缺少明确生命周期，可能重复请求或读取过期发布版本的数据。
- `space-page.tsx` 与内联样式文件承担过多职责，继续修改容易产生重复逻辑和回归。

## 目标

1. 以团队发布版本作为能力、智能体角色和流程的唯一运行权限来源。
2. 删除旧白名单运行逻辑、model、schema 文件和数据库旧表。
3. 保证自动保存失败后保持脏状态并自动重试，同时向界面暴露保存状态。
4. 将 ReactFlow 的拖动、平移和缩放保留在本地瞬态状态，仅在交互结束时提交持久状态。
5. 让节点渲染缓存、能力目录缓存和能力表单缓存具有可验证的命中条件和生命周期。
6. 在不重写整个画布的前提下，拆分稳定边界，降低主文件复杂度。

## 非目标

- 不重做画布视觉设计。
- 不改变现有画布 JSON 协议和节点类型。
- 不引入新的状态管理库、缓存库或后端依赖。
- 不在本次任务中执行构建或测试命令；由用户手动完成浏览器功能验证。

## 权限与旧数据清理

### 能力

能力目录和能力参数表单读取当前项目同步后的团队发布版本。运行接口继续使用 team service 已有的 `team_powers` 校验，不再读取 body 画布能力白名单。

### 智能体

画布智能体节点实际保存团队角色和对应的 `agent_id`。运行前同步项目当前发布版本，并校验：

- 角色存在于当前发布快照且已启用；
- 请求中的 `role_id` 与角色一致；
- 请求中的 `agent_id` 与该角色的 `agent_id` 一致；
- 智能体本身仍处于启用状态。

这样删除旧智能体白名单后不会放宽到任意智能体。

### 团队

运行当前项目团队或显式选择其他团队时，保留现有的团队启用、发布版本归属和已发布检查，不再叠加 body 画布团队白名单。

### 退役数据

删除以下代码和数据：

- `CanvasPower`、`CanvasAgent`、`CanvasTeam` model；
- body service 的 `AllowedPower*`、`AllowedAgent*`、`AllowedTeam*`；
- project service 的 `requireBody*` 和排序过滤逻辑；
- 三个 `data/table/shemic_bot_body_canvas_*.json` schema 文件；
- 数据库中的 `shemic_bot_body_canvas_power`、`shemic_bot_body_canvas_agent`、`shemic_bot_body_canvas_team` 表。

Dever 当前不会因 model 完全消失而自动删除旧表，因此数据库清理必须显式执行，并在执行后查询确认三张表均不存在。

## 自动保存状态机

自动保存按画布分类维护修订号，而不是每轮扫描、序列化全部画布：

- 本地变更增加该画布的 `revision` 并标记 dirty；
- 520ms 静默窗口后提交该画布快照；
- 成功时仅在提交修订仍是最新修订时标记 saved；
- 失败时保留 dirty，记录错误，按有上限的退避时间重试；
- 新变更到达时取消旧计时并以最新快照重新调度；
- 卸载或切换项目时取消计时和过期请求结果。

保存状态只表现为 `saving`、`saved`、`error`，失败不能伪装成成功。

## ReactFlow 热路径

`CanvasWorkbench` 维护 ReactFlow 本地节点和 viewport：

- 外部持久画布变化时同步本地节点；
- `onNodesChange` 只更新本地 ReactFlow 节点，不提交父级完整画布；
- `onNodeDragStop` 一次性提交最终节点位置；
- `onMove` 只更新本地缩放显示；
- `onMoveEnd` 一次性提交最终 viewport；
- 连线、删除、新增等离散操作仍立即提交。

持久化比较使用修订/脏标记，不在指针移动事件中 `JSON.stringify` 整个画布。节点运行输出保留现有持久行为，本次不删除可能影响刷新恢复的字段。

## 节点渲染缓存

移除基于 `cached.data === nodeData` 的无效缓存。节点数据按节点 id、节点对象引用、选中态、单节点运行态和稳定 controller 引用构造；回调通过稳定 controller/context 提供，避免父组件每次渲染制造整棵节点树的新函数。

节点组件使用明确的 props 比较，单个节点运行状态变化只更新相关节点。

## 请求缓存

### 能力目录

项目工作区加载后预取一次。打开右键菜单不强制请求；进入能力视图时仅在缓存不存在或超过 TTL 时刷新。并发请求共享同一个 promise，项目或 release 变化时失效。

### 能力表单

移除模块级永久 Map，改为有上限的工作区缓存。key 包含 `project_id`、`release_id`、`flow_id`、`power_id/power_key` 和 `target_id`。项目或 release 变化时清空，超过容量时淘汰最早条目。

## 文件拆分

采用渐进拆分，不重写页面：

- `space-autosave.ts`：画布 dirty/revision、保存调度和状态；
- `space-catalog-cache.ts`：能力目录与能力表单缓存；
- `space-workbench.tsx`：ReactFlow 本地交互状态和画布控件；
- `space-add-node-menu.tsx`：右键添加菜单；
- `space.css`：从 React 内联 `<style>` 迁出的静态样式。

主页面继续负责工作区编排、项目数据和对话框组合。运行/SSE 逻辑已有独立模块，本次只清理重复入口，不做大规模协议重写。

## 失败处理与兼容

- 发布版本缺少角色、角色与智能体不匹配时返回明确错误，不回退到旧白名单或任意智能体。
- 能力目录刷新失败时保留上次成功缓存并提示错误。
- 自动保存冲突继续交给后端 `base_revision` 处理，前端保留脏状态供重试或后续刷新。
- 删除旧表前先移除所有调用点并做静态引用检查。

## 验证方式

遵循项目要求，不运行 `npm run build` 或任何测试命令。实施后仅进行：

- `gofmt` 和前端已有格式化工具的定向格式化；
- `rg` 静态引用、重复逻辑和旧表检查；
- 查看运行日志确认热加载没有新增编译错误；
- 查询数据库确认三张旧表已删除；
- 向用户提供视频能力、智能体权限、保存失败重试、拖拽缩放等手工验证清单。
